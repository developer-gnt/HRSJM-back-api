# Phase 9 — Donation Financial / Payment Integration (7 APIs)

## Scope
The financial layer of donations, mirroring the proven Phase 5 pattern: donation payments with backend-only gateway verification, receipt generation, accounting posting (`Dr Bank/Cash / Cr Donation Income`), and full-refund via controlled mirrored reversal. Includes a minimal `donations` table scaffold (Arshad-owned going forward — same precedent as Phase 4's `CreateArshadModulesSchema`) and a `donation_refunds` record table per phases.md's table list.

## 1. Entities & enums
- `src/modules/donations/entities/donation.entity.ts` (`donations` — scaffold): `donor_name` varchar(150), `donor_mobile` varchar(15), `donor_email` varchar(150) nullable, `cause` varchar(255) (approved-cause catalogue is TBC — free text for now), `amount` numeric(12,2), `status` varchar(30) default 'PENDING' (PENDING/SUCCESS/REFUNDED — final donation-status enum is Arshad's/TBC), `remark` text nullable, extends `BaseEntity`.
- `src/modules/donation-payments/entities/donation-payment.entity.ts` (`donation_payments`): `donation_id` FK RESTRICT, `user_id` uuid nullable FK SET NULL (walk-in/guest donors may have no account), `amount` numeric(12,2), `payment_method` varchar(50) default 'ONLINE', `payment_status` (existing `PaymentStatus`: PENDING/SUCCESS/FAILED/REFUNDED), gateway fields (`gateway_order_id`, `gateway_payment_id`, `gateway_signature` varchar, `gateway_response` jsonb), `payment_date`, `notes` — mirrors `membership_payments`.
- `src/modules/donations/entities/donation-refund.entity.ts` (`donation_refunds`): `donation_payment_id` FK CASCADE, `amount` numeric(12,2), `reason` text nullable, `reversed_entry_id` uuid nullable (links the REVERSAL accounting entry), `refunded_at` timestamptz.
- Reuse: `PaymentStatus` from common enums; `ReferenceType.DONATION_PAYMENT` + `ACCOUNT_CODES.DONATION_INCOME ('4003')` already exist in the accounting module; receipts/payment_transactions already have `donation_payment_id` columns (no FK yet — Phase 9 migration adds the constraints).

## 2. Migration `CreateDonationsSchema`
Generate via `migration:generate`, review, extend with: FKs from `receipts.donation_payment_id` (SET NULL) + `payment_transactions.donation_payment_id` (CASCADE) into `donation_payments`; unique index on `receipts.donation_payment_id`; indexes (donation_id, user_id, payment_status); permissions block `...0000000008xx` — `donation.read`, `donation.create`, `donation.manage` (Arshad's future CRUD, seeded ready), `donation.refund` — all granted to ADMIN. Run + verify (`migration:show`, DB checks, app boot); log issues in the Migration Issue Log.

## 3. DonationPaymentsService + Controller (6 APIs)
- `POST /api/v1/donation-payments` — validates donation exists; amount defaults to `donation.amount`, server-validated > 0 (never trusted from frontend); creates payment PENDING + `payment_transactions` row (INITIATED) — mirrors Phase 5 create. No permission (open to any authenticated donor); admin sees all.
- `GET /api/v1/donation-payments` — self-scoped (own payments) unless admin; filters: payment_status, donation_id, date range + pagination meta.
- `GET /api/v1/donation-payments/:id` — ownership check like Phase 5 getById (admin or own).
- `POST /api/v1/donation-payments/:id/verify` — idempotent (already-SUCCESS returns existing); inside one `dataSource.transaction`: status→SUCCESS + `payment_transactions` row (SUCCESS) + receipt (`HRSJM-REC-...` numbering, `receipt_type: 'DONATION'`, `donation_payment_id` set, `accounting_entry_id` linked) + **accounting posting** Dr Bank (1001)/Cash (1002 by payment_method), Cr Donation Income (4003), reference `DONATION_PAYMENT` + donation status → 'SUCCESS'. Posting failure rolls back everything.
- `PATCH /api/v1/donation-payments/:id/status` — admin (`payment.manage_status`); SUCCESS delegates to verify (offline pattern); **REFUNDED via this endpoint is rejected** — refunds must go through the refund endpoint so accounting stays consistent; FAILED allowed.
- `GET /api/v1/donation-payments/:id/receipt` — mirror Phase 5 getReceipt (strip password_hash).

## 4. Refund — DonationsService + DonationsController (1 API)
- `POST /api/v1/donations/:id/refund` — `@RequirePermissions('donation.refund')` (admin-only).
- Full-refund policy (per decision; partial refunds stay TBC): only donations with a SUCCESS payment can be refunded; idempotent — already-refunded returns current state with 409-free semantics... implemented as: already REFUNDED → ConflictException `DONATION_ALREADY_REFUNDED`; no SUCCESS payment → BadRequest `DONATION_NOT_REFUNDABLE`.
- In one transaction: `posting.reverse(manager, journal.id)` (mirrored REVERSAL — `Dr Donation Income / Cr Bank-Cash`) + payment_status → REFUNDED + donation status → REFUNDED + `donation_refunds` record with `reversed_entry_id`. Audit both. Posted entries stay immutable.
- Scaffold note: donations CRUD (create/list/update) stays with Arshad — e2e seeds donations via SQL; no donation CRUD APIs added (API count stays exactly 7).
