# Phase 6 — Accounting Foundation: COA + Entries + Ledger (10 APIs)

## Scope
Build the double-entry financial engine in a new `src/modules/accounting` module: Chart of Accounts CRUD, read-only accounting entries with controlled reversal, derived ledgers with running balance, a **reusable transactional posting service** (for Phases 5/7/8/9), seed a minimal baseline COA + permissions via migration, and wire Phase 5 payment verification to post accounting entries. Follow every step of rule.md §2.10 (entity → generate → review SQL → run → verify → log issues).

## 1. Entities, enums, constants (`src/modules/accounting`)
- `enums/accounting.enums.ts` — const-object enums (varchar-stored, per codebase pattern): `AccountType` (ASSET/LIABILITY/INCOME/EXPENSE/FUND_EQUITY), `EntryType` (JOURNAL/REVERSAL), `ReferenceType` (MEMBERSHIP_PAYMENT, RENEWAL_PAYMENT, DONATION_PAYMENT, MANUAL_RECEIPT, MANUAL_EXPENSE).
- `accounting.constants.ts` — canonical account codes for money-flow wiring: `BANK='1001'`, `CASH='1002'`, `MEMBERSHIP_INCOME='4001'`, `RENEWAL_INCOME='4002'`, `DONATION_INCOME='4003'`, `OTHER_INCOME='4004'`, `OTHER_EXPENSE='5001'`.
- `entities/account.entity.ts` (`accounts`): `account_code` varchar(20) unique-nullable, `account_name` varchar(100) unique, `account_type` varchar(20), `parent_account_id` uuid self-FK nullable (SET NULL), `description` text, `is_active` boolean default true, extends `BaseEntity`.
- `entities/accounting-entry.entity.ts` (`accounting_entries`): `entry_number` varchar(30) unique, `entry_date` timestamptz, `entry_type` varchar(20) default JOURNAL, `reference_type` varchar(30), `reference_id` uuid, `description` text, `reversal_of_entry_id` uuid self-FK nullable, extends `BaseEntity`.
- `entities/accounting-entry-line.entity.ts` (`accounting_entry_lines`): `accounting_entry_id` FK CASCADE, `account_id` FK RESTRICT, `debit_amount`/`credit_amount` numeric(12,2) default 0 with the standard parseFloat transformer, `line_description` text nullable, `line_number` int, extends `BaseEntity`.
- Indexes: `idx_accounts_type`, `idx_entries_date`, `idx_entries_reference (reference_type, reference_id)`, `idx_lines_entry`, `idx_lines_account`; **partial unique indexes**: `(reference_type, reference_id) WHERE entry_type='JOURNAL'` (idempotent posting) and `reversal_of_entry_id WHERE NOT NULL` (one reversal max).

## 3. AccountingPostingService (exported, the core)
- `postEntry(manager, {entryDate, referenceType, referenceId, description, lines, userId})` — takes the **caller's transactional EntityManager** so Phases 5/7/8/9 post inside their own DB transaction. Validates: ≥2 lines; each line exactly one side > 0; **Σdebit = Σcredit compared in integer paise** (`Math.round(x*100)`, no float drift); accounts exist and `is_active`. Generates `JE-YYYYMMDD-#####` from the sequence, inserts entry + lines with audit fields. Duplicate reference (unique violation) → returns the existing journal entry (idempotent, safe for gateway callbacks).
- `reverse(manager, entryId, userId)` — rejects missing/already-reversed entries; creates a mirrored REVERSAL entry (sides swapped) with `reversal_of_entry_id` set. Posted entries are never edited or deleted.

## 4. Accounts API (5 endpoints, `AccountsController` @Controller('accounts'))
- `POST /accounts` — parent must exist and share the same `account_type`; unique name/code; audit logged. Permission `account.create`.
- `GET /accounts` — filters: `account_type`, `parent_account_id`, `is_active`, `search` (name/code) + page/limit meta. `account.read`.
- `GET /accounts/:id` — with parent + children summary. `account.read`.
- `PATCH /accounts/:id` — name/code/description/parent only; `account_type` immutable after creation. `account.update`.
- `PATCH /accounts/:id/status` — deactivate blocked while active child accounts exist; postings to inactive accounts rejected at posting service, so history stays intact. `account.manage_status`.

## 5. Entries + Ledger API (`AccountingController` @Controller('accounting'))
- `GET /accounting/entries` — filters: `reference_type`, `reference_id`, `entry_type`, date from/to + pagination; entries with lines. `accounting_entry.read`.
- `GET /accounting/entries/:id` — detail with lines (account name/code/type) + reversal link if reversed. `accounting_entry.read`.
- `POST /accounting/entries/:id/reverse` — returns the reversal entry. `accounting_entry.reverse`.
- `GET /accounting/ledger` — global ledger: `from_date` + `to_date` required (BRD §24), `account_id`/`entry_type`/`reference` optional filters; rows: date, entry_number, account, description, debit, credit, running balance (per-account normal-side convention: ASSET/EXPENSE debit-positive; LIABILITY/INCOME/FUND_EQUITY credit-positive). `ledger.read`.
- `GET /accounts/:id/ledger` (in AccountsController) — per-account ledger, optional date range; opening balance computed via aggregate before the window when `from_date` given, running balance carried across pages. `ledger.read`.
- All ledger data derives strictly from `accounting_entry_lines` joins — no balance tables, no side calculations.

## 6. Phase 5 wiring (membership-payments.service.ts `verify()`)
Inside the existing `dataSource.transaction` block, right after receipt creation: call `postEntry(manager, …)` with `referenceType=MEMBERSHIP_PAYMENT`, `referenceId=payment.id`, lines = Dr Bank/Cash (mapped from `payment_method`: CASH→1002, else→1001) / Cr Membership Income (4001) for `payment.amount`; set `savedReceipt.accounting_entry_id = entry.id`. Any posting failure rolls back the whole verify transaction. Update `membership-payments.service.spec.ts` accordingly.
